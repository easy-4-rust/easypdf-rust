# v0.3.0 Writer 引擎抽象与 krilla 第二后端 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: rust-api-design, rust-workspace, rust-testing

**Goal:** 在不改变任何公共 API 的前提下，为 easypdf-writer 引入引擎抽象层，并新增 krilla 作为第二生成后端（feature gate）。解决 printpdf 组合的三个结构性问题：字体子集化缺失（CJK 体积）、PDF/X 合规地基缺失、lru unsound 传递依赖锁死。printpdf 保留为默认后端（0.x 兼容承诺），krilla 在 1.0 窗口评估翻转默认。

**Architecture:** easypdf-writer 内部引入 `WriteEngine` trait（内容生成引擎接口）+ 自有 `WriterOp` 中间表示（IR）。`PdfWriter` 公共 API 不变，内部按 feature 选择引擎实现：`writer-krilla`（新，krilla 实现）/ 默认（printpdf 实现）。`PageBuffer.ops` 从 `Vec<printpdf::Op>` 改为 `Vec<WriterOp>`（自有 IR），Spill 序列化随之与 printpdf 解耦。

**Tech Stack:** Rust 1.88 / edition 2024，krilla（crates.io 最新稳定版，pdf-writer 系，Typst 生态），现有 lopdf 0.44（读侧不变），serde（WriterOp spill 序列化），criterion（双后端基准）。

## Global Constraints

- **公共 API 零变化**：api-snapshots 五个 crate 的 diff 必须为零（PageBuffer 若在快照中，其字段类型变更需先确认可见性——若 pub 则此为 0.3.0 的 minor 破坏性变更，需在 CHANGELOG 标注）。
- 1522+ 测试不回归；双后端各自全绿。
- `#![deny(unsafe_code)]`、pedantic clippy、中文 doc 注释、mod.rs 纯净——全部延续现行规范。
- krilla 依赖必须通过 deny.toml 许可证检查（krilla 系为 Apache-2.0/MIT，预期无问题）。
- printpdf 路径行为保持字节级不变（这是兼容承诺，不允许"顺手优化"）。
- 每个 Wave 结束跑全量门禁（fmt/check×2/clippy/test/doc/MSRV/public-api），绿了才进下一 Wave。

## 关键发现（代码核对，2026-08-16）

- `PdfWriter` 的 18 个 pub 方法全部只引用 easypdf-core 类型（PdfText/PdfFont/PageSize/PdfMetadata）——**printpdf 零泄漏到方法签名**，抽象层只需处理内部表示。
- 唯一泄漏点：`backend.rs:37` 的 `PageBuffer.ops: Vec<printpdf::Op>`（pub 字段）。已核对 `api-snapshots/easypdf-writer.txt`：**PageBuffer 不在公共 API 快照中**（未从 lib.rs re-export），Wave 1 为纯内部重构，零公共 API 影响。
- printpdf 0.12.5 为最新版，无升级路径（docs/printpdf-evaluation.md）；azul-layout hard-pin lru 0.16 无法 patch，这是引入 krilla 的独立动机。
- 现有 0.3.0 计划（compliance-converters）的 PDF/A 任务依赖本计划：PDF/A 要求字体嵌入与 XMP，krilla 的 PDF/X 支持是其地基。
